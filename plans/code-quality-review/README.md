## Overall verdict

The codebase is in good shape for its size and age. It is spec-driven and consistently
structured, with a clear pure-Dart core / Flutter app split and a thorough test suite (≈ 1,200
server tests in 130 files, 125 test files in the Sheets app, 232 in Slides, property tests and
fuzzers in the sync/OT layers).
The command-and-undo discipline (spec 08) holds almost everywhere. Raw SQL is parameterized
throughout, and secrets handling and file-URL signing are done carefully.

The weaknesses are concentrated in a few recurring patterns, so most of them can be fixed by
fixing the pattern once (see the themes below):

1. **Authorization edge cases in Drive and sharing.** These are the only High security findings. Each endpoint has an access check; the gaps are in *multi-step* flows (move → trash → purge, register on another kind's space, copy with comments).
2. **Server concurrency hygiene.** Full-row writes from stale reads, `on Exception` catches that let `Error`s escape, check-then-act limits, unrenewed job leases. One of these can brick a Write document (`updateMeta`).
3. **O(document) work per edit in all three editors.** Invalidation is too broad: a global "state changed" signal rebuilds the editor scaffold and keymap, Slides re-resolves every slide on deck changes, and Sheets rescans the used range and the dirty set. The rendering architectures themselves (painter grid, scene graph, Fenwick indexes) are sound.
4. **Heavy work on the wrong isolate.** Server PDF exports and diffs run on the main isolate with timeouts that don't cancel. Client exports and PDF image work run on the UI thread.
5. **Duplication between Sheets, Slides and Write.** On the server: AI run scaffolding ×5, headless caches ×2, change-log consumers ×2, MCP helpers. On the client: clipboard, PDF view, uploads, conflicts dialog, find bar, command UI. Also two implementations of the same rule in several places (suggestion rewriter, number formats, collation, Markdown), which already disagree.
6. **Unbounded caches and maps.** About 15 hand-rolled LRUs and static maps that never evict. `session.caches` is never used.
7. **No benchmarks where the specs require them.** The Sheets core benchmarks, the Write performance suite and the Slides render-invalidation tests don't exist. Most performance findings would have been caught by them.
8. **Vendored forks.** `serverpod_offline_sync` [RL], `dart_eval` (pins the workspace's analyzer) and `super_editor` (86 patch sites; its test dependencies leak fonts into every web app).

## Things done well (keep doing)

- **Server**
  - `AccessService` is the single permission source; it returns `notFound` so ids don't leak, and role lookups are batched.
  - HMAC file-URL tokens are compared in constant time and bound to purpose, file, user, size and expiry.
  - Hashed MCP tokens with scopes enforced twice; constant-time webhook HMAC; an SSRF-safe script fetch proxy.
  - All raw SQL is parameterized; cluster locks are advisory transaction locks.
  - Recurring jobs are scheduled idempotently under a cluster lock.
  - Exactly-once change-log receipts; bounded headless caches with incremental patches.
- **Sync and OT**
  - Durable outboxes written before sending.
  - A sound `FOR UPDATE` OT commit with unique indexes as a backstop.
  - Viewport-first loading.
  - Convergence fuzzers and property tests.
- **Client architecture**
  - Pure-Dart cores shared by app, server and exports.
  - A painter-based virtualized grid with no widget per cell.
  - O(log n) geometry with Fenwick trees.
  - A scene graph shared by every Slides renderer.
  - Time-sliced spellcheck and pivots.
  - Lazy fonts and a lazy 3D backend.
- **Discipline**
  - Commands and undo are respected almost everywhere.
  - Consistent Given/When/Then test names; injectable clocks.
  - Almost no TODO/FIXME in `lib/`.
  - Documented vendored patches.
